한 사람이 잘못된 API 키를 넣었을 뿐인데, 그 순간부터 모든 사용자가 막힌다면 어떨까요?

서킷 브레이커를 처음 붙이던 날 제가 하마터면 만들 뻔한 구조가 딱 그거였습니다.

안녕하세요, 고준서입니다. study-helper는 PDF를 올리면 LLM으로 학습 노트와 퀴즈를 만들어 주는 서비스인데, 혼자 만들고 있어요. 사용자는 Claude, GPT, TimelyGPT 중 하나를 고르고 자기 API 키를 넣습니다. 2026년 3월 31일에 프로바이더를 하나에서 셋으로 늘리면서 클라이언트마다 서킷 브레이커를 하나씩 뒀는데, 이번 글에서는 그 브레이커가 무엇을 실패로 세고 무엇을 세지 않기로 했는지를 케이스별로 풀어보려 합니다.

## 브레이커 하나에 프로바이더 하나

브레이커는 프로바이더별로 프로세스 안에 하나씩 있습니다. 연속 실패가 5회에 닿으면 열리고, 60초 뒤에 요청 하나를 통과시켜 반쯤 닫힌 상태를 시험해요. 세 클라이언트가 같은 클래스를 복사해서 갖고 있습니다.

```python
# app/services/anthropic_client.py:24-31
class _CircuitBreaker:
    """Simple half-open circuit breaker for the Anthropic API."""

    FAILURE_THRESHOLD = 5     # consecutive failures before opening
    RECOVERY_TIMEOUT = 60     # seconds before attempting half-open
```

열려 있는 동안 그 프로바이더 호출은 API를 건드리지 않고 503으로 바로 끝납니다. 다른 두 프로바이더의 브레이커는 별개라 영향이 없고요. 재시도는 브레이커 바깥에서 `MAX_RETRIES=2`로 돕니다. 1초, 2초 지수 백오프이고, 두 번 더 해 보고도 안 되면 500으로 끝내죠.

여기까지는 교과서 그대로입니다. 문제는 "실패"가 뭐냐는 거였어요.

```mermaid
flowchart TD
    R[생성 요청] --> C[프로바이더 클라이언트]
    C --> E{예외 종류}
    E -->|401 인증 실패| U[사용자 상태: 브레이커 제외, 재시도 제외]
    E -->|429 레이트리밋| U
    E -->|400 + credit| T[503으로 번역: 브레이커 제외, 재시도 중단]
    E -->|5xx, 타임아웃, 연결 실패| B[브레이커에 실패 기록]
    B --> F{연속 5회?}
    F -->|예| O[브레이커 열림, 60초간 503]
    F -->|아니오| RT[최대 2회 재시도]
```

*그림 1. 예외가 어디로 가는지에 따라 브레이커에 기록되기도, 안 되기도 합니다.*

## 케이스 A. 401, 인증 실패

이 서비스의 키는 서버 것이 아니라 사용자 것입니다. 그러면 인증 실패는 프로바이더의 상태가 아니라 그 사용자의 상태죠.

401을 실패로 세면 어떻게 될까요? 한 사용자가 오타 난 키로 다섯 번 시도하면 브레이커가 열리고, 그 순간부터 60초 동안 멀쩡한 키를 가진 다른 사용자들까지 503을 받습니다. 프로바이더는 아무 문제가 없는데 서비스가 스스로 문을 닫는 셈이에요.

그래서 인증 예외는 브레이커에 기록하지 않습니다.

```python
# app/services/anthropic_client.py:93-98
    except anthropic.AuthenticationError as exc:
        # Auth failures do not count toward the circuit breaker
        raise GenerationError(
            "Invalid Anthropic API key. Please check your key and try again.",
            status_code=401,
        ) from exc
```

## 케이스 B. 429와 503

같은 논리로 429도 세지 않습니다. 레이트리밋은 대개 키 단위로 걸리니 역시 사용자의 상태거든요. 브레이커에 기록되는 것은 프로바이더 쪽 문제로 볼 수 있는 셋뿐입니다. 5xx 계열 상태 오류, 타임아웃, 연결 실패.

재시도도 같은 선을 긋습니다. `generate_with_retry`는 401, 429, 503을 받으면 다시 시도하지 않고 그대로 올려요. 키가 틀렸는데 2초 기다렸다가 또 보내 봐야 결과는 같고, 레이트리밋에 걸렸는데 바로 또 보내면 리밋만 더 깊어지니까요. 503은 브레이커가 이미 열렸다는 뜻이라 재시도해 봐야 같은 503입니다.

## 케이스 C. 400인데 credit

Anthropic은 크레딧이 떨어지면 400을 돌려줍니다. 코드로만 보면 잘못된 요청이죠. 그대로 두면 재시도 대상이 되고 브레이커에도 실패로 쌓입니다. 둘 다 틀렸어요. 크레딧이 없는 건 요청 형식 문제도 아니고 프로바이더 장애도 아니니까요.

그래서 메시지에 "credit"이 있으면 503으로 바꾸고 브레이커는 건드리지 않습니다.

```python
# app/services/anthropic_client.py:104-109
    except anthropic.APIStatusError as exc:
        if exc.status_code == 400 and "credit" in str(exc.message).lower():
            raise GenerationError(
                "서비스에 일시적인 문제가 발생했습니다. 잠시 후 다시 시도해주세요.",
                status_code=503,
            ) from exc
```

503으로 올리면 재시도 루프가 바로 멈추고 사용자에게는 "잠시 후 다시" 메시지가 갑니다. 솔직히 이 메시지는 정확하지 않아요. 잠시 후에도 안 되는 문제거든요. OpenAI와 TimelyGPT 쪽은 402와 403을 같은 자리로 보내고 "quota exceeded or billing issue"라고 적어 줍니다. 이 분기는 `test_call_claude_credit_error_returns_503` 같은 테스트로 고정돼 있고, 세 클라이언트의 브레이커와 401 처리도 각각 테스트가 있습니다.

## 케이스 D. TimelyGPT의 두 단계 인증

TimelyGPT는 API 키를 바로 쓰지 않습니다. 키로 access token을 먼저 받고, 그 토큰으로 생성 요청을 보내요. SDK 소스를 읽어 흐름을 그대로 옮겼는데, 이 이식과 세 클라이언트의 브레이커 구현은 Claude와 같이 작업했습니다. 토큰은 키별로 55분 캐시합니다.

그러면 401이 두 층에서 날 수 있겠죠? 토큰 교환에서 나면 키가 틀린 것이고, 생성 요청에서 나면 토큰이 만료됐을 가능성이 있습니다. 두 번째 경우는 캐시를 비워서 다음 시도가 재인증하게 했어요.

```python
# app/services/timely_client.py:170-175
    if resp.status_code == 401:
        # Token may have expired; evict cache so next retry re-authenticates
        _token_cache.pop(api_key, None)
        raise GenerationError(
            "TimelyGPT authentication failed. Please verify your API key.",
            status_code=401,
        )
```

여기서도 401은 브레이커 밖입니다. 다만 "다음 시도"가 자동으로 오지는 않아요. 401은 재시도 제외 목록에 있으니 사용자가 다시 눌러야 재인증이 됩니다. 토큰 캐시는 모듈 변수라 워커마다 따로 있고, 작업 기록에도 워커 간 공유가 안 된다는 점을 "기능상 문제 없음"으로 적어 뒀습니다.

## Gemini 무료 플랜을 만들고, 지우다

사실 네 번째 프로바이더가 있었습니다.

3월 24일에는 사용자 키 없이 쓰는 Gemini 무료 플랜이 있었어요. 서버가 Gemini 키 여러 개를 풀로 들고 라운드로빈으로 돌리고, 429를 맞은 키는 쿨다운에 넣는 구조였습니다. 이틀 뒤 쿨다운을 고정 60초에서 15초, 30초, 60초로 늘어나는 지수 방식으로 바꾸고 응답의 Retry-After를 우선하게 했고요. 3월 31일에는 rate limit 재시도를 최대 4회 루프로 늘렸습니다. 그날 GPT와 TimelyGPT를 붙였으니 플랜은 넷이었죠.

4월 8일에 키 풀이 소진돼 UI에서 무료 플랜을 숨겼습니다. 같은 날 법적 위험을 검토하다가, 서버가 키 풀을 돌려 무료로 제공하는 방식이 구글 API 약관 위반 소지가 있다고 판단해 완전히 지우기로 했어요. 결정은 한 줄이었습니다. 모든 플랜을 사용자 본인 키 방식으로 통일.

4월 9일 커밋에서 `llm_provider.py` 361줄이 사라졌고, `plan` Literal에서 `"free"`가 빠졌습니다. 지금 코드에 남은 Gemini의 흔적은 `json_utils.py` 첫 줄 주석 하나예요.

돌이켜보면 재미있는 게, 브레이커가 401을 세지 않는 이유는 "키가 사용자 것"이라는 전제였잖아요. 무료 플랜은 그 전제를 깨는 유일한 플랜이었고, 결국 다른 이유로 사라졌습니다.

## 마치며

브레이커는 가용성 장치입니다. 프로바이더가 응답을 못 할 때 요청을 빨리 실패시켜 다른 플랜으로 넘어갈 시간을 벌어 주는 것이지, 돌아온 응답이 맞는지는 전혀 보지 않아요. 응답 검증은 별도 검증기가 하고 그 검증기에도 구멍이 있었다는 이야기는 [다른 글]({{ "/2026/04/25/llm-output-validation-korean-tokenizer/" | relative_url }})에 있습니다. 자소서 초안을 쓰다가 이 둘을 섞어 "산출물 검증" 사례로 브레이커를 든 적이 있는데, 그때 스스로 적은 대로 격리 설계는 가용성 기준이지 정확성 기준이 아니에요.

그리고 가용성 장치로서도 완결되지 않았습니다. 브레이커가 열려 있어도 요청을 다른 프로바이더로 자동으로 보내지 않아요. 503을 받은 사용자가 플랜을 바꿔 다시 눌러야 합니다. 상태는 프로세스 메모리에만 있어서 워커가 재시작되면 실패 횟수가 0이 되고, 워커가 둘이면 브레이커도 둘이라 한쪽만 열릴 수 있죠. 코드 주석에 "multi-worker deployments use Redis-backed state instead"라고 적어 두고 하지 않았습니다. 열림과 닫힘을 세는 지표도, 상태를 보는 엔드포인트도 없어서 브레이커가 실제로 열린 적이 있는지는 로그를 뒤져야 알 수 있어요.

그래도 하나는 분명하게 남았습니다. 실패를 세기 전에 "이게 누구의 실패인가"를 먼저 물어야 한다는 것. 사용자 키를 받는 서비스라면 이 질문 하나가 브레이커를 보호 장치로 만들기도, 장애 전파 장치로 만들기도 합니다.

혹시 비슷한 구조를 만들고 계신 분들께 도움이 되면 좋겠습니다. 감사합니다.
